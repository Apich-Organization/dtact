## 2023-10-27 - [Redundant atomic loads in worker loops]
**Learning:** In the hot `poll_mailboxes` loop of the scheduler, the previous code likely calculated the current local queue length (`local_queue_len()`) on every mailbox chunk popped, involving repeated atomic loads of `local_head` and `local_tail`. While `local_head` is an immutable invariant for the single worker thread within `poll_mailboxes`, `local_tail` is only mutated by `push_batch` on the same worker thread. Passing these values down and accumulating changes locally saves redundant atomic operations.
**Action:** When adding elements to local queues sequentially, compute changes locally (e.g. `cur_len += added`) and pass this cached state directly to functions like `route_chunk` rather than making those functions do full atomic re-evaluations.

## 2023-10-27 - [Redundant atomic loads in dispatch_loop]
**Learning:** In `Worker::dispatch_loop`, the `loop` continuously re-reads `local_tail` from the atomic variable. However, `local_tail` is only ever modified by this worker thread (via `push_local`, etc., when tasks are enqueued locally). Wait, during `dispatch_loop`, the current fiber could yield and enqueue things to the local queue, or receive things from the external mailbox. But `local_tail` can be mutated by the current thread during `((*target_ptr).switch_fn)`. So we can't completely avoid loading `local_tail`. However, we can cache `local_tail` locally and only reload it when we reach `head == tail`, to see if new things were added.
**Action:** Cache `local_tail` and only reload it when necessary to minimize atomic loads.
